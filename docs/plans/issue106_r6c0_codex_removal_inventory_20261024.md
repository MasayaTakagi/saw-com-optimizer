## 1. Binding decision and classification key

The [Issue #75 owner policy](issue75_legacy_codex_retirement_decision_20261024.md) supersedes the former requirement to qualify a Pi/exact-session or detached-worker replacement before deleting old Codex. The old queue and callback have no future product use and are to be removed. C0 is the authorized docs/static preflight; code changes need a separately bounded C1 work order after C0 independent review.

The classifications below describe recommended C1+ dispositions, not completed changes:

- **`DELETE`** — active Codex-specific implementation/dispatch and its Codex-only tests, after read-only history and source-fingerprint handling are reviewed.
- **`MOVE/REPLACE`** — mixed CLI/lifecycle behavior that needs a non-Codex owner or explicit fail-closed replacement.

- **`RETAIN_ACTIVE_SAFETY`** — process, storage, worktree or checkpoint safety that is not Codex-specific.
- **`STOP_FOR_OWNER`** — a live-run, historical fingerprint, scientific-evidence or contract ambiguity that must be resolved before the affected deletion/cutover.

A repository search describes checked-in callers only. User-level Codex settings, external C2C checkout/scripts, undocumented invocations and current processes remain **UNKNOWN**. The checked-in `.codex/hooks.json` has an empty `hooks` object; that does not prove the absence of external hook use.

## 6. Process safety, roots and live-run blocker

The old `orchestration/` package is not synonymous with Codex. Preserve or separately move these owners:

- `process_runner.py` starts and supervises detached processes; `pid_utils.py::pid_exists` is used by status/recovery/closeout.
- `active_runs.py::{git_common_dir,registry_directory,active_runs_for_worktree,register_active_run,release_active_run}` owns the shared registry at the Git common directory under `sawopt-active-runs`; production launch registers a run, worktree checks consult it, and publication/admin closeout release it.
- `persistent_storage.py::validate_persistent_run_location` discovers all Git worktrees and fails closed on unsafe/existing paths; Stage4C and orchestration use it.
- `worktree_safety.py::{audit_worktree,remove_worktree}` locks, reads the registry and prevents removal while a run is active; `scripts/worktree_safety.py` is a direct wrapper (`scripts/worktree_safety.py:1–24`, `scripts/README.md`).
- `run_manager` atomic writes/locks, optimizer completion, process errors, status transitions, checkpoint finalization in `worker.py`, and administrative closeout have non-Codex safety responsibilities.

`orchestration.cli status <run_id>` currently reads manifest/status and continuation ledger through `format_status` and probes recorded PID liveness; it is an observational path but is **not** a global active-run inventory and requires a chosen run path. `recover`, `launch --resume`, `review`, `confirm-queue`, and `mark-review-published` mutate files/status or can spawn/send work; they are not metadata-only. Worktree audit/removal is a separate safety command, not a substitute for enumerating all live run roots. None was invoked here.

Before any destructive C1 cutover, the owner policy requires a separate, bounded **metadata-only active-run inventory**. Candidate roots/fields for that future authorization (not accessed under C0):

1. The explicit repository/worktree/host/user allowlist; the Git common-dir `sawopt-active-runs` registry and its registry metadata/active records (`run_id`, `run_dir`, `source_worktree`, `source_head`, state/timestamp).
2. For listed candidate run roots only, control metadata `run_manifest.json`, `status.json`, and `continuation_delivery.json` sufficient to identify schema/mode/status/PID/queue-ledger state. Do not open optimizer payloads, checkpoints, raw artifacts, cell arrays, full logs, credentials, environment variables or Codex/Pi session content.
3. If expressly authorized, a minimal OS process identity/liveness check for listed PIDs; never use a PID check alone as proof of no active run, and do not inspect process environment/secrets. Contradictory, inaccessible, unknown-version, unregistered or externally hosted entries stay `UNKNOWN` and stop destructive action.

No global absence claim is possible from a repository scan: lost control manifests, unregistered/external run roots, another host/user and user-level hooks remain outside this C0 scope. Do not infer that current active runs/processes are zero. If an active old worker/queue dependency is found later, stop and obtain owner direction; this is a finite safety gate, not a requirement to build Pi replacement indefinitely.
