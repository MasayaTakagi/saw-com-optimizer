## 1. Owner-selected architecture and current evidence

The binding architecture is reduced hybrid C: a harness-independent Python CLI and detached Python worker, one SQLite WAL lifecycle ledger for the isolated synthetic proof, manual operator-initiated recovery after host/WSL restart, existing optimizer checkpoint and R5 raw/review owners, and a later optional Pi exact-session adapter. Do not add an always-running supervisor, broker, automatic host startup/replay, native-Windows guarantee, or Rust/Numba layer. The ledger, optimizer run/checkpoint, R5 raw/review, and Pi session are separate authorities. A Pi session is not a scientific `run_id`, checkpoint, FE ledger, or authorization.

## 3. Three noninterchangeable continuity contracts

### A. Detached task continuity (same running host)

**Identity/state owner:** a task/run ID and immutable request in one lifecycle ledger; each process attempt has its own attempt ID/fence and positively checked host/boot/PID/start/argv identity. The SQLite synthetic ledger currently owns only countdown status/progress; the optimizer checkpoint store and R5 raw manifest remain separate. A UI/terminal/Pi disconnect is not a task transition.

**Required behavior:** explicit user launch; read-only `status` and `attach`; cooperative `stop` addressed to the exact current attempt; no duplicate start for an identical idempotency key; no auto-restart from status/help/import/reattach. After WSL/host reboot, the operator explicitly requests recovery; no background service or automatic replay is required or authorized. Unknown process identity or a launch/spawn/claim gap is `LAUNCH_AMBIGUOUS`, `PROCESS_IDENTITY_UNKNOWN` or `RECOVERY_REQUIRED`, not proof of completion/death.

**Evidence boundary:** #80/#81 proves the bounded countdown survives the launching CLI exit on Linux/WSL2 while that host remains alive; #82/#83 proves explicit countdown-only recovery. Neither is a scientific Worker qualification or host-reboot test. Missing coverage for a future scientific executor is the durable binding of its authorization/run manifest, evaluator/result commit and publication state to task attempts.

### B. Same-run optimizer/checkpoint/FE recovery

**Identity/state owner:** preserve the original `run_id` and authorization reference/scope, immutable execution source SHA, effective config/model/search-grid/validation-grid hashes, topology/design domain, exact expected roster, seed/RNG implementation, optimizer/backend/runtime identity, budget/hard limit, checkpoint state and per-cell unique-FE/cache/result accounting. Same-run recovery cannot silently alter source/config/grid/seed/budget/roster or create a new scientific run. Checkpoint state belongs to `optimization`/`io.checkpoints`; the evaluator/result journal must separately prove which external evaluations are durably committed.

**Required behavior:** validate optimizer state and all identity hashes before resuming; preserve PCG64/L-SHADE state, counters, cache/result attribution and budget; never count an uncommitted result as completed. A commit boundary between evaluator return, durable result record and optimizer checkpoint must be explicit. If an in-flight external evaluation may have completed but no committed result can prove it, set `RECOVERY_AMBIGUOUS` and STOP; never silently re-evaluate it. Any manual resolution or new budget/condition needs separate explicit authorization.

**Evidence boundary:** current checkpoint classes and unit/integration tests establish storage/state serialization and deterministic fixture resume, not the end-to-end scientific run contract. R5 records caller-reported counts and checks declared limits/reconciliation; it cannot independently observe that a COM/FE call occurred. No task-ledger ↔ optimizer-checkpoint ↔ evaluator-result transaction, real COM/FE restart, or formal Q1 qualification is proven. All Q1 gates remain unpassed.

### C. Exact agent/Pi session continuation

**Identity/state owner:** a protected mapping from a local task association to exact `pi_session_id`, private session-file reference and file identity, expected Pi version, branch leaf/entry cursor, and the last correlated RPC request/response and dispatch state. This mapping is separate from `run_id`, checkpoint, authorization and review package. Session bodies/credentials never enter scientific manifests or logs.

**Required behavior:** reopen only the exact stored session (never `--continue`, picker or unchecked create-on-miss); verify returned ID/path/version and branch/cursor; distinguish request ACK from `agent_settled`; record a possible accepted-but-unsettled prompt as `DISPATCH_AMBIGUOUS` and do not resend automatically. Missing/mismatched session is an explicit non-PASS status, not a newly created session relabelled as resume. Pi availability must not gate detached Worker execution or scientific checkpoint recovery. Any agent action that can write, publish, launch or change data still needs the relevant human authorization.

**Evidence boundary:** #84/#85 proves fake-transport protocol/state-boundary behavior only. `pi_session.py` has no production transport or prompt-dispatch method and is not wired into the CLI/worker. #86 did not achieve a correlated state response; #91 did not start Pi because the identity preflight is blocked. Real exact-session reopen, branch continuity, real ACK/settled event behavior and in-flight prompt recovery remain unqualified.
