**Audited source:** verified `main` `7a490fd999386b821734fee60fd92eb0f61b075f` (PR #76). This document is a design proposal and read-only source/capability audit. It does not change legacy runtime behavior, select an owner-approved architecture, qualify a replacement, or authorize any real scientific task.

## 1. Executive recommendation

Recommend **Option C — a hybrid**:

1. Make a **harness-independent durable executor and persisted run/task ledger** the sole authority for launch, process supervision, same-run optimizer recovery, status, stop, artifact export, and publication state. A supported OS supervisor/scheduler starts and watches that executor; a ChatGPT/Codex/Pi UI is never required for scientific computation to continue.
2. Add **Pi as an optional, separately persisted agent-session adapter** for monitoring/review and approved continuation of agent work. Identify the exact Pi session (and branch cursor) explicitly. A Pi session is never a scientific `run_id`, a checkpoint, a launch authorization, or proof that an optimizer resumed.
3. Keep the current exact-thread Codex queue/callback as a **temporary compatibility bridge** until the replacement has passed synthetic fault qualification and the owner approves cutover. Preserve old manifest v1–v4 interpretation and historical source/evidence; do not flip defaults or delete the bridge in this design phase.

This provides the strongest path to all three distinct requirements without coupling them: detached task survival, deterministic same-run scientific resume, and agent conversation/session continuation. It has more operational components than retaining the current queue, but does not inherit the queue's exact-thread harness dependency as the product's durable execution authority. **The recommendation is pending explicit owner selection and implementation authorization.**

## 3. Evidence and current limits

### 3.1 Local Pi Code capabilities (version-specific)

Read-only local introspection found the installed `pi` executable at `~/.pi/agent/bin/pi`, version **1.4.0**. `pi --help` exposes `--continue`, `--resume`, `--session <path|id>`, `--session-id <id>`, `--session-dir <dir>`, `--no-session`, `--mode rpc`, `--print`, and the regular CLI options. The installed 1.4.0 package documentation was checked: `docs/sessions.md`, `docs/cli.md`, `docs/rpc.md`, `docs/rpc-commands.md`, `docs/session-format.md`, and `docs/security.md`.

What those sources support:

- Sessions are saved automatically unless `--no-session` is used. `--session-dir` selects a persistent store; `--session <path|id>` opens a specific session; `--continue` selects the latest session for the current project, and `--resume` opens an interactive picker. `--session-id` may **create** a session if it does not exist, so it must not be used as an unchecked recovery lookup.
- RPC is a documented long-lived child process with JSONL requests, correlated responses, events, and explicit session commands. `get_state` reports `sessionFile` and `sessionId`; `switch_session` can select an exact path; `get_entries` supports an entry-ID cursor across client restarts; `agent_settled` is the documented signal that Pi will not continue automatically.
- A successful RPC `prompt` response means only accepted/queued/handled, not that agent work completed. A client must subscribe to events before prompting, consume the event stream, and wait for `agent_settled` where completion matters.
- Session files are conversation trees and can include prompts, assistant output, tool calls/results, file contents, and extension messages. Treat the session store as sensitive user data; never copy transcripts into scientific manifests/review packages or expose them in logs.

What is **not** established by the installed docs or this read-only check:

- No Pi CLI/RPC process was started, no prompt or model request was sent, and no session was created, reopened, read, exported, or modified. Therefore exact-session startup, authentication, `agent_settled` handling, event replay, and a post-process-restart round trip are **documented but not runtime-qualified** here.
- RPC describes a child process controlled over pipes; the docs do not promise that a process survives parent/host termination, that Pi automatically restarts an interrupted RPC task, or that an in-flight prompt can be replayed exactly once after a crash. No documented Pi endpoint is a scientific checkpoint store or experiment authorization mechanism.
- `--continue` is not a stable run/session association: it means “most recent for this project.” Unattended continuation must use a persisted exact session ID/path, not `--continue` or the interactive picker.

**Classification:** `PI_CLI_EXACT_SESSION_RESUME = DOCUMENTED_AVAILABLE / NOT_RUNTIME_QUALIFIED`; `PI_RPC_SESSION_CONTROL = DOCUMENTED_AVAILABLE / NOT_RUNTIME_QUALIFIED`; `PI_DURABLE_DETACHED_EXECUTION = NOT PROVIDED BY THE DOCUMENTED INTERFACE`; `PI_INFLIGHT_PROMPT_RECOVERY_AND_EXACTLY_ONCE_DISPATCH = UNKNOWN / NOT GUARANTEED`; `PI_SCIENTIFIC_CHECKPOINT_RESUME = NOT A PI CAPABILITY`.

### 3.2 Existing SAW optimizer/orchestration capabilities

The existing orchestration is a useful implementation baseline, not the proposed final design:

- `orchestration.process_runner.launch_detached` starts a Python worker in a new POSIX session or with Windows detached-process flags, redirects logs, and returns a PID. `orchestration.run_manager` persists status and `worker_pid` / `optimizer_pid`; `pid_utils.pid_exists` checks PID liveness. This is terminal-disconnected process launch, **not** a supervised durable queue or host-reboot recovery service. A PID alone does not distinguish PID reuse; the current launch/status record does not bind a process start time and host boot epoch.
- `orchestration.cli` implements launch/status/recover/resume and gates for the current legacy paths. `_resume_launch` reattaches if stored PIDs appear live, otherwise marks the run orphaned and launches the worker with `--resume` from selected failure/orphan states. Do not treat this as evidence that any active run was safely inventoried or that all process/restart races are solved.
- The worker executes the existing optimizer command, records process completion, finalizes checkpoint stores after successful completion, and routes old schemas to callback or schema-v4 queue behavior. The schema-v4 exact-thread queue has a durable one-shot delivery ledger and receiver-confirmation/publication steps. It is coupled to old manifests and the legacy CLI; it is not a harness-independent scheduler.
- `io.checkpoints.CheckpointStore` provides a rolling `latest`/`previous` store, validates payloads, fsyncs a staged JSON checkpoint before rotation, and can recover a valid retained generation. `optimization.checkpoint_session.LShadeCheckpointSession` binds the store to L-SHADE and retains a legacy direct-file path without migration. L-SHADE state version 4 includes the RNG state, population/archive/memory, counters including unique evaluations, frequency-grid version/state, budget horizon and a source/config fingerprint. Load-time checks reject unsupported state versions and some source/config/horizon mismatches. This is necessary infrastructure for scientific resume but alone does not prove run-manifest/grid/roster identity, crash-safe evaluator transactions, or end-to-end resume qualification.
- R5 `io.experiment_store` and `reporting.experiment_review` are future-only, synthetic-test-backed APIs. Their manifests can bind source/config/grid identity, expected cell rosters and checkpoint observations, but they are not a live scheduler/queue and are not a legacy manifest or old-checkpoint reader. They do not automatically replace `orchestration` state. `experiment_store` currently imports `fcntl` and relies on POSIX directory-fd/no-follow operations; native Windows portability is **not established** by its presence. Do not advertise R5 as native-Windows portable without a separately reviewed and qualified backend.
- The official development baseline is Ubuntu/WSL2 with Python 3.12. Existing `process_runner` has POSIX and Windows launch branches, but that does not qualify the complete storage/supervisor/recovery stack on native Windows. WSL process lifetime is bounded by the WSL VM; a systemd user service can supervise while the distro runs, but Windows restart/`wsl --shutdown` recovery requires a separately configured and tested host-to-WSL startup mechanism (for example an owner-approved Windows Task Scheduler trigger). Neither mechanism is currently part of this issue's code changes.

### 3.3 Scientific exactly-once boundary

A checkpoint restores optimizer state; it does not automatically make an external evaluation transactional. A crash can occur after an evaluator has performed work but before the result and optimizer checkpoint are durably committed. For a purely deterministic synthetic evaluator, a durable idempotency ledger keyed by `(run_id, cell_id, canonical_design, scientific_input/grid_sha)` can prove unique-result accounting and reuse the stored result. If an evaluation is in-flight and the system cannot prove whether it completed, safe behavior is `RECOVERY_AMBIGUOUS` and **no automatic re-evaluation**; require a separately authorized resolution. Do not claim exactly-once real COM/FE just from replaying an L-SHADE checkpoint. No such evaluator call was made in this audit.

### Recommendation details and trade-offs

Use **C** with **A as the mandatory base and B as an optional adapter**. Keep the project’s officially supported runtime initially at Ubuntu/WSL2. Treat native Windows as unsupported for the full executor/store until path safety, locking and restart semantics are qualified there. If the owner requires recovery across Windows/WSL host restart, add a separately scoped Windows-to-WSL startup supervisor and synthetic fault tests; otherwise state clearly that a stopped host leaves work `RECOVERY_REQUIRED` until the owner starts the supported service. In both cases, do not silently restart or create a new run.

Avoid putting the agent process in charge of scientific execution. A Pi disconnection may mark agent-monitor state `DISCONNECTED` while the run remains `RUNNING`; a scientific process exit may mark the run terminal while the Pi session is `AVAILABLE` or `AMBIGUOUS`. Never collapse these identities or statuses.

## 5. Proposed testable contract (for later owner-approved implementation)

### 5.1 Durable identities and persistence owners

- **`run_id`**: stable identity of one immutable scientific request; assigned and committed before a worker can spawn. Bind experiment ID, explicit authorization reference/scope, immutable execution-source SHA, effective scientific config/model/search-grid/validation-grid hashes, topology/design domain, seed, optimizer/runtime identity, budget/hard limit, expected cell roster, raw-store location and creation time. Reuse this exact ID on same-run resume; a new design, seed, budget, source or condition is a new run and needs separate authorization.
- **`task_id`**: stable identifier for the durable executable task; initially one-to-one with `run_id`, but distinct in schema so future non-scientific tasks cannot masquerade as scientific runs.
- **`attempt_id` / `fencing_token`**: monotonically increasing process attempt and lease generation. A resumed attempt does not create a new `run_id` or reset FE counters.
- **Process identity**: record `(host_id, OS boot/startup epoch, pid, process start time, executable/source identity, attempt_id)`. PID-only liveness is insufficient. Linux can use boot ID and `/proc` start time; a Windows implementation needs process creation time and a host epoch. If the platform cannot establish identity, status becomes `PROCESS_IDENTITY_UNKNOWN`; never infer death/relaunch from PID absence alone.
- **Persistence separation**: the durable executor ledger owns task queue, authorization reference, process identity, attempt/lease, transition journal, errors and launch idempotency. The run's immutable manifest owns scientific inputs/provenance; the checkpoint/result store owns optimizer/evaluator state; the R5 review package owns compact export identity; a Pi session store owns agent conversation history. These stores cross-reference stable IDs and hashes but are not interchangeable. The run ledger may reference a Pi session ID/path and last observed entry cursor; it must not duplicate session bodies or credentials.
- A SQLite WAL ledger is one candidate for atomic local queue/lease/outbox transactions; an external service/SQL backend is not required by this recommendation. A versioned filesystem journal is an alternative if it can prove equivalent multi-process atomicity and recovery. The owner must approve the persistence implementation, storage location, backups and threat boundary before code work. R5's raw experiment manifest must not be extended implicitly into a scheduler database.

### 5.2 Operations and error/status semantics

Command spellings below are proposals, not current supported product commands.

| Operation | Contract | Principal fail-closed statuses/errors |
|---|---|---|
| `launch <frozen-request> --authorization <ref>` | Require explicit user action and immutable authorization. Validate the request, frozen identities, allowed evaluator, persistent destination and resource policy. Atomically create the request/run identity and queue record before spawning. Same idempotency key + same exact request returns the existing `run_id`; same key with different payload is `IDEMPOTENCY_CONFLICT`. Keep three orthogonal state axes rather than an overloaded single status:

- **Task/run**: `PLANNED → AUTHORIZED → QUEUED → STARTING → RUNNING → {STOP_REQUESTED → STOPPED_CHECKPOINTED, COMPLETED, FAILED, ORPHANED}`; recovery may return a verified `ORPHANED`/checkpointed run to `QUEUED` for a new `attempt_id`, or stop at `RECOVERY_REQUIRED` / `RECOVERY_AMBIGUOUS`. `attach` is not a state transition. Terminal completion never silently returns to RUNNING.
- **Review/publication**: `NOT_REQUESTED → PENDING → EXPORTED → PUBLISHING → PUBLISHED`, with explicit `EXPORT_FAILED`, `PUBLISH_FAILED`, or `PUBLISH_AMBIGUOUS`. Package integrity, readiness, independent review, owner acceptance and publication are distinct facts.
- **Agent session**: `NOT_ATTACHED`, `AVAILABLE`, `PROMPT_PENDING`, `RUNNING`, `SETTLED`, `DISCONNECTED`, `SESSION_MISSING`, `SESSION_IDENTITY_MISMATCH`, `DISPATCH_AMBIGUOUS`, `FAILED`, or `UNSUPPORTED`. Persist exact `pi_session_id` and branch leaf/cursor separately from task/run IDs. If a Pi prompt was accepted but the acknowledgement/settlement was lost, do not automatically send it again; inspect/resolve only through the explicitly approved procedure.

### 5.3 Lease, locks, crash and recovery rules

Use an exclusive per-run lease with a monotonic fencing token, instance ID, host/boot identity, PID + process-start identity, acquisition/heartbeat time and attempt ID. All mutations require the current fencing token. A timeout alone does not authorize lease stealing: compare process identity/boot epoch and any service lock; if uncertain, block and request operator disposition. A PID reused by another process must never be adopted as the worker.

Persist queue/outbox intent before starting a subprocess. On crash between `Popen` and PID registration, the worker must present a run/attempt token (e.g. a validated environment/argv token) before it can claim the lease; recovery scans only the authorized task ledger and reconciles the unique attempt. If it cannot distinguish “child never started” from “child started but record lost,” use `LAUNCH_AMBIGUOUS`, not a second launch.

Checkpoint writes must be atomic, fsynced and validated before a checkpoint generation becomes authoritative. Bind all checkpoint streams to the same `run_id` and scientific identity hashes; preserve both latest and previous valid generations. Record the last fully committed evaluator result and cumulative unique-FE accounting in a durable result journal before optimizer state advances past it. Require all expected cells to have an explicit roster/status; do not infer missing cells as successful. If the evaluator may have completed an external operation but its result commit is uncertain, mark `RECOVERY_AMBIGUOUS` and forbid automatic replay. This is a future software/scientific correctness contract requiring explicit review, not a promise about current code.

Host restart reconstruction reads only the durable task/manifest/status/checkpoint metadata and verified checkpoint headers/identities, then either queues the same run for an approved resume or marks it blocked. It does not change source/config/seed/budget, regenerate identity, create a new FE, finalize/publish, or claim progress that was not durable. If service startup, clock/lease identity, or persistent storage health is uncertain, fail closed.

### 5.4 Agent/Pi session identity and dispatch rules

- Persist a mapping `(task_id, run_id if applicable, agent_kind, exact Pi version, pi_session_id, session_file_reference, active_leaf_entry_id, last_acknowledged_task_id, dispatch_state)`. Treat absolute session paths as sensitive local references; never commit user paths or transcript contents.
- Start/reopen with an explicit exact session path/ID and explicit session directory, not `--continue` or the picker. If the ID/path is absent, mismatched or not readable, report `SESSION_MISSING`/`SESSION_IDENTITY_MISMATCH`; do not create a replacement via `--session-id` and label it a resume.
- In RPC clients, install the event listener before prompt dispatch, correlate responses by request ID, keep consuming JSONL, and wait for `agent_settled`. The durable task service must continue if the Pi child/UI disconnects. RPC request IDs are not a cross-process deduplication guarantee.
- Session continuation may carry a structured, immutable review handoff with exact `run_id`, package hash, allowed operations, forbidden launch/re-run action and review stage. Session continuation may not supply scientific authorization, alter a frozen request, or perform an implicit run/resume/publish. Human approval is required before any agent action with write, network, publication or process-launch authority.
- If the same Pi session can be reopened but an in-flight accepted prompt cannot be shown to have settled, classify it as `DISPATCH_AMBIGUOUS`; do not duplicate prompt or side effects. A fresh Pi session and a signed/verified immutable handoff is a distinct continuation mode, not a pass for exact-thread/session resumption.
- Apply Pi's documented security boundary: the agent/tools/extensions inherit the OS user's access; project trust is not a sandbox. Use a dedicated least-privilege account or OS/container restriction if needed, narrow tools, isolate credentials, and keep transcript/session storage out of review artifacts.

## 7. Synthetic-only validation plan and crash matrix

All implementation qualification below is **future work**, using only an injected deterministic evaluator, temporary external raw roots, temporary fake Git repositories, fake Pi/RPC subprocesses, and disposable fixtures. Do not run COM/FE or real optimizer research. Retain the existing full locked science/regression suite and its Haswell test-only pin for later code changes; this design document does not require numerical tests.

| Fault / scenario | Test setup and expected result |
|---|---|
| Launcher/agent/UI exits immediately after launch | Fake long-running worker writes durable progress. Parent exits; supervisor keeps it alive; a fresh CLI attaches by the same `run_id` without spawning another worker. |
| Duplicate/concurrent launch | Race two starts using the same idempotency key and frozen request: exactly one run/task and one worker; loser gets the same identity. Same key/different request fails `IDEMPOTENCY_CONFLICT`. |
| Crash before/after queue record fsync; crash after spawn before PID record | Inject each boundary. Recovery reconciles the attempt token and lease; does not launch a second child if first may exist. Unresolvable state is `LAUNCH_AMBIGUOUS`. |
| PID reuse / foreign PID / lost child | Fake process table reuses a PID with different start time/boot epoch. Status must not attach, stop or adopt it. Mark `ORPHANED` only on positive identity proof; otherwise `PROCESS_IDENTITY_UNKNOWN`. |
| Two workers contend for one run; stale lock/lease | Competing attempts and stale-heartbeat fixtures. Fencing token admits one writer; time expiration alone cannot steal a potentially live lease. Stale lock cleanup never removes a newly acquired lock. |
| Child crash while optimizing; safe checkpoint exists | Inject crash after a durable complete optimizer/evaluator boundary. Reattach/resume same `run_id`, source/config/grid/seed/budget/roster; compare deterministic final optimizer state and FE accounting with an uninterrupted synthetic run. No new run ID or additional budget. |
| Evaluator returns before result/checkpoint fsync; crash after each fsync/replace boundary | Inject fault before evaluation, during evaluation, after evaluator return, after result-ledger write, after checkpoint temp fsync, after latest/previous rotation. Reload validates only complete bound state. Ambiguous in-flight operation is blocked, never silently re-evaluated. |
| Checkpoint corruption, wrong source/config/grid/horizon, missing/cross-cell stream | Corrupt or mismatch synthetic fixture. Fail closed; no cold-start fallback, no mutation/repair of old checkpoint, no FE and no partial roster success. |
| Host/service restart | Unit/mock supervisor restarts with durable queue and boot-epoch change. Approved synthetic task resumes same identity only after validation; missing service/platform/startup config leaves `RECOVERY_REQUIRED`. Any later real OS restart test must be a separate owner-approved isolated synthetic test. |
| Stop during a safe boundary and forced stop | Cooperative stop flushes/checkpoints and reports `STOPPED_CHECKPOINTED`; a forced kill without validated checkpoint reports `STOPPED_UNCHECKPOINTED`/`RECOVERY_REQUIRED`, never success. |
| All-cell roster/error accounting | Predeclare cells; crash/fail selected synthetic cells; manifest/status retains each as completed, failed, not-run or incomplete with typed failure. Never infer missing results as successful or publish as complete. |
| Export/publication exactly-once logical behavior | Build a synthetic R5 review package in a temp root and temp Git remote. Crash before commit, after commit, after push and before ledger acknowledgement; retry reconciles by immutable package SHA/commit. No overwrite, duplicate logical publication or premature `READY_FOR_REVIEW`. |
| Pi session exact identity and RPC protocol (mocked first) | Fake Pi CLI/RPC emits interleaved responses/events, accepted prompt, failure, exit and `agent_settled`. Validate exact ID/path mapping, event listener before prompt, request correlation, `get_entries` cursor and no duplicate prompt after ambiguous acknowledgement. A fake process test does not qualify real Pi support. |
| Optional real Pi session round trip | Only if the exact Pi 1.4.0 CLI/RPC path is still available and owner authorizes an isolated test: use a new temporary session directory, unique synthetic session ID, deterministic local test provider, no MCP/extensions/tools with side effects, and dummy prompt text only. Create and reopen that specific session, verify ID/path and a harmless test marker, clean only the test-owned temp root. If no offline deterministic provider/safe test profile is available, mark this test `NOT RUN / UNSUPPORTED`, not PASS; do not use account history or provider credentials in CI. |
| No authorization / completed-run resume / new run via session restore | Negative CLI tests with missing authorization and fixtures for completed, mismatched and old read-only manifests. All reject without process launch or file mutation. Session `--continue`/restore alone cannot launch/resume. |

### Recovery categories

- **Recoverable:** one verified worker is dead; a complete, identity-matched durable checkpoint/result ledger exists; no ambiguous in-flight evaluation; run is not terminal; authorization still covers the exact run; one lease can be acquired.
- **Wait/reconcile:** worker/service may be alive but identity is incomplete; publication ack is uncertain; Pi prompt may be accepted but unsettled; filesystem/host epoch is unavailable. No launch, FE, resend or publish retry until positive reconciliation.
- **Blocked/owner disposition:** corrupt/missing checkpoint; source/config/grid/roster/budget mismatch; old manifest is read-only; evaluator work is ambiguous; terminal run; authorization expired/not found; external storage/writer safety uncertain. Preserve state and report exact cause.

## 8. Read-only legacy inventory feasibility

A repository/source audit can identify code paths and which metadata a future diagnostic would need, but **cannot establish that no active legacy runs or user-level hooks exist**. Issue #73/#74 already show why a static import scan or empty project hook config is insufficient.

A separately owner-authorized **metadata-only** live-run inventory could potentially report active legacy runs without opening checkpoint payloads or raw result artifacts if it has an explicit allowlist and approved roots. It would need to read the Git common-dir active-run registry, each candidate's control `run_manifest.json`/`status.json` and one-shot delivery ledger, and query OS process identity (PID + creation/start time + boot epoch). It must not read `optimizer_run_dir` contents, checkpoint bodies, raw arrays, logs, session contents or modify status/locks. This approach still may miss old runs whose control manifests are lost, whose external persistent roots are unknown, or whose worker is outside the inspected host; therefore it cannot prove global absence by itself.

Before such inventory, obtain a separate owner permission specifying:

1. exact repositories/worktrees, host(s), user(s), active-run registry, run roots and environment sources that may be listed;
2. allowed metadata fields and process-table inspection, with prohibition on reading raw/checkpoint/session bodies;
3. read-only handling of inaccessible, symlinked, unknown-version or contradictory entries (report `UNKNOWN`, never repair);
4. output destination/redaction, retention and who reviews the result; and
5. a stopping rule if discovering a possible live run would otherwise invite attaching, resuming, stopping, or opening its artifacts.

No such live-state or user-level hook inventory was attempted here.
